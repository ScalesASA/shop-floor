Explainer

Skills and routines

Official order from the use-cases doc is the whole layer. Skip a step and you will schedule a sloppy path.

TL;DR

  1. Job, sources, output format, and boundaries in the description.
  2. One real task with a safe scope.
  3. Correct until it is reviewable without you.
  4. Save the working process as a skill. Test it on a second input.
  5. Create a routine only after retries and failure cases are defined.
  6. Keep consequential external actions behind approval.
Step 1 — Demonstrate, then name the skill

Walk the Bot through a multi-step path once across your systems. It can persist that path. Invoke later with /. A skill that still needs you to remember the prompt is not a skill yet.

Step 2 — Second input is the exam

Run the skill on a different week, different page, or different account list. If the output shape breaks, fix the skill before any clock is involved.

Step 3 — Routines stop at a review list

Official sales example: schedule a nightly research routine that stops at the review list. That is the SMB pattern. A routine that publishes at 06:00 is an incident.

Stop-line. No routine that sends, publishes, or spends. Failure case must be written: “if the site is down / the cite is missing / the page changed, stop and ask.”

Generic drill

15 minutes. Take yesterday’s five-bullet summary path. Save it as a skill. Run it on a second document. Compare the two outputs. If the second is sloppy, do not schedule anything.

Personal build — weekly EHS skill

Turn FireGuard’s table+brief path into a skill named /ehs-week. Inputs: bluesteelco.com public pages + this week’s regulatory headlines the Bot is allowed to search. Output: brief in /workspace/bluesteelco/briefs/YYYY-MM-DD.md plus a draft FAQ, unpublished. Failure: if a claim cannot be sourced, mark “cite needed” and stop. Do not create the Monday routine until you have run /ehs-week on two different dates.

Done when two dated briefs share a shape and neither touched the live site.
